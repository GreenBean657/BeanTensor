BeanTensor

A machine-learning framework built from scratch in C++23 — CPU (AVX2 / AVX-512 / BF16), CUDA, and HIP, with zero external ML dependencies.

Capstone walkthrough · November 2026 · GreenBean

Why build this?

  • Every framework hides its machinery behind C++ and CUDA binaries — this one hides nothing.
  • Goal: a PyTorch-class training stack (autograd, layers, optimizers, data pipeline) where every kernel, every dispatch decision, and every rounding rule is ours and documented.
  • Acceptance bar is empirical: end-to-end MNIST/CNN results must land within 1pp of a pinned PyTorch reference on the same data and hyperparameters.

Architecture at a glance

  • Tensor core: async error model — ops queue onto a work-stealing thread pool, errors materialize at sync().
  • CPU dispatch tiers: scalar → AVX2 → AVX-512/BF16, gated at runtime through one cached CPU-feature probe.
  • Reverse-mode autograd over a Kahn-ordered graph, with a per-call gradient dtype and user-pinnable leaf grad dtypes.
  • GPU backends: CUDA (43 TUs) and hand-mirrored HIP; conversion kernels are bit-exact against the CPU dispatcher by contract.
  • Reduction autotuning: per-device block-size cache with a no-cache = compiled-defaults determinism contract.

Feature surface

  • Layers: Linear, Conv2d, BatchNorm, Max/AvgPool2d, Flatten, Dropout, Relu/Gelu, Sigmoid, Tanh, Softmax — He and Xavier init.
  • Training: softmax-CE / MSE / BCE losses, Adam + SGD, grad scaler, train/eval semantics.
  • Dtypes: fp64 → fp32 → fp16/bf16 (incl. packed) → full integer ladder, with clamp/flag-exact conversion rules.
  • Tooling: versioned .bt checkpoints (weights/grads/Adam moments, CRC-verified), pybind11 Python bindings, DataLoader + CSV + MNIST ingestion.

Op-level vs PyTorch (CPU)

  • Median-of-5 benchmark harness wired into the test suite as a smoke test — a family that stops producing rows fails the build.
  • Covers elementwise, GEMM, reductions, losses, conv2d, max-pool, batch-norm — same shapes as the PyTorch comparator (comparison/bench_pytorch.py).
  • Full published table with repro commands: docs/benchmarks.md.
  • Gradient parity vs PyTorch (bit-level tolerance analysis) is its own doc: docs/gradient-parity.md.

Engineering discipline

  • GPU test gate: every GPU-touching test runs through a flock-serialized wrapper — one wedged driver killed a desktop session once; it can never happen twice.
  • Pre-push gate: clean tree, one signed commit, agentic-marker audit, SHA-pinned workflows, full CPU matrix green on the exact tree — enforced by a hook, bypass only by declared exception.
  • Whole-project TSAN-clean; pool stress/deadlock suites looped, not run once.
  • Tests derive from the machine, not the dev box: sizes, thread counts, and tolerances come from runtime detection — a test that passes here and fails on a grader's box is treated as a test defect (two real CI failures were fixed exactly this way).

btui — the training TUI

  • Standalone stdlib-only curses app (python/btui.py): keyboard-driven layer-stack editor, data + hyperparameter panels, no code required.
  • Live framed layout: vertical loss graph on a reserved centerline, pool-throughput graph with honest idle semantics, edit-while-running with weight reuse by name + shape.
  • Checkpoint save levels including a share-safe strip; .bt import restores the embedded training config.
  • Telemetry: VRAM + SM utilization polled at 2 Hz during GPU runs, rendered in the Training box.

What the CI failures taught

  • A loss-ring assertion assumed a slow dev box; a 2-vCPU runner overflowed the 240-entry window — fixed by asserting the capped invariant.
  • A mean-reduction tolerance was accused of flakiness; measurement showed the real bug: sequential fp32 sums saturate past 2²⁴. Chunk partials now accumulate in fp64 — exact on any host.
  • Both shipped through the gate and ended green — the process caught what the happy path never would.

Where it goes next

  • Weight-format interop (safetensors export/import) for the HF/PyTorch ecosystem.
  • Streaming data ingestion for datasets that exceed RAM.
  • Windows as a first-class build target alongside Linux (x86_64; ARM stays out of scope).
  • Python API reference docs with runnable examples.
